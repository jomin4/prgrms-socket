# ch05 — 폴링 vs SSE

> 코드 없는 개념 챕터. ch04 에서 직접 본 `[]` 응답 더미를 숫자로 환산하고,
> SSE 가 그 구조를 어떻게 뒤집는지 정리한다.

---

## 1. 지금 우리 구조 (폴링)

```
   브라우저                              서버
      │                                   │
      ├──── GET ?afterChatMessageId=4 ───▶│  filter { id > 4 }
      │◀──────────── []  ─────────────────┤  없음
      │        (1초 대기)                  │
      ├──── GET ?afterChatMessageId=4 ───▶│
      │◀──────────── []  ─────────────────┤  없음
      │        (1초 대기)                  │
      │            ⋮  (계속)              │
```

**브라우저가 계속 묻는다.** 서버는 할 말이 없어도 매번 대답해야 한다.

핵심 문제: **서버는 새 메시지가 생긴 걸 이미 알고 있는데 알려줄 방법이 없다.**
HTTP 는 클라이언트가 물어야만 서버가 답하는 구조이기 때문.

---

## 2. 비용을 숫자로

요청 하나를 뜯어보면 (ch04 Network 탭에서 본 그것):

**요청 (브라우저 → 서버) ≈ 500 byte**
```http
GET /api/v1/chat/rooms/2/messages?afterChatMessageId=4 HTTP/1.1
Host: localhost:8080
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...
Accept: */*
Accept-Language: ko-KR,ko;q=0.9
Accept-Encoding: gzip, deflate, br
Connection: keep-alive
Referer: http://localhost:8080/
```

**응답 (서버 → 브라우저) ≈ 150 byte + 본문 2 byte**
```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2
Date: Fri, 07 Aug 2026 16:30:00 GMT

[]
```

> **정보량 2 byte 를 얻으려고 650 byte 를 쓴다. 실제 데이터 비율 0.3%.**

| 접속자 | 1분 | 1시간 | 1시간 트래픽(대략) |
|---|---|---|---|
| 1명 | 60 요청 | **3,600** | 2.3 MB |
| 10명 | 600 | **36,000** | 23 MB |
| 100명 | 6,000 | **360,000** | 230 MB |

그리고 이 요청들은 전부 **톰캣 스레드를 점유하고, 컨트롤러를 실행하고, `filter` 를 돌고,
JSON 을 직렬화한다.** 결과가 `[]` 라는 걸 알아내기 위해서.

---

## 3. 그런데 지연도 남아 있다

```
시각      사건
──────────────────────────────────────────
10.000s   ┬ 폴링 (결과 [])
10.100s   │   ← 홍길동이 "안녕" 작성 (서버엔 이미 있음)
          │
          │   ⏳ 900ms 동안 화면에 안 보임
          │
11.000s   ┴ 폴링 → 그제서야 받음
```

| | 값 |
|---|---|
| 최선 | ~0초 |
| **평균** | **0.5초** (= 간격 ÷ 2) |
| 최악 | 1초 |

간격을 0.2초로 줄이면 지연은 0.1초가 되지만 요청은 **5배**.

```
        낭비 ◀──────────────────▶ 지연
       (간격 짧게)          (간격 길게)
```

**둘을 맞바꾸는 구조 자체가 한계다.** 어느 쪽도 공짜로 좋아지지 않는다.

---

## 4. SSE 는 무엇을 뒤집나

SSE(Server-Sent Events)는 **응답을 끝내지 않는 HTTP** 다.
새 프로토콜이 아니라, 평범한 `GET` 인데 서버가 응답을 다 쓰고 닫는 대신 **열어둔다.**

```
   브라우저                              서버
      │                                   │
      ├─ GET /sse/connect/chat__room__2 ─▶│
      │◀── 200 OK                         │
      │    Content-Type: text/event-stream│  ← 응답을 안 닫음
      │    (연결 유지 ...)                 │
      │         💤 조용함 = 트래픽 0        │
      │                                   │  ← 홍길동이 메시지 작성
      │◀──── event: chat__messageCreated ─┤  즉시 push
      │      data: {...}                  │
      │         💤 조용함 = 트래픽 0        │
```

연결이 열린 뒤 흐르는 바이트는 이것뿐:

```
event: chat__messageCreated
data: {"id":7,"createDate":"2026-08-07T16:22:10.12","chatRoomId":2,"writerName":"홍길동","content":"안녕"}

```
(빈 줄 = "이벤트 끝" 표시. `\n\n` 이 구분자)

**HTTP 헤더가 없다.** 연결이 이미 열려 있으니 매번 `User-Agent`, `Accept`, `Cookie` 를
다시 보낼 이유가 없다. 2절의 650 byte 오버헤드가 **0** 이 된다.

## 5. 숫자 비교

**10명이 1시간 접속, 그중 메시지 100개 오감**

| | 폴링 (1초) | SSE |
|---|---|---|
| 브라우저→서버 요청 수 | **36,000** | **10** (연결만) |
| 서버→브라우저 전송 | 36,000회 (대부분 `[]`) | 1,000회 (100 × 10명) |
| 조용할 때 트래픽 | 계속 발생 | **0** |
| 헤더 오버헤드 | 매 요청 650B | 최초 1회 |
| **평균 지연** | **0.5초** | **~수십 ms** |
| 서버 스레드 | 요청마다 점유 후 반납 | **점유하지 않음** (아래 참고) |

> 📌 **정정 (ch06 에서 확인)** — SSE 가 "커넥션당 스레드를 유지한다" 고 적었던 것은 틀렸다.
> `SseEmitter` 를 반환하는 순간 Spring 은 **서블릿 비동기 모드**로 전환하고 **요청 스레드를
> 즉시 반납**한다. 소켓만 열려 있고 스레드는 잡혀 있지 않다. 톰캣 NIO 커넥터가 소수의
> poller 스레드로 유휴 커넥션 수천 개를 관리한다.
> 만약 커넥션당 스레드를 붙잡는 구조였다면 SSE 는 실용성이 없었을 것이다.

**낭비와 지연을 맞바꾸던 구조가 깨진다. 둘 다 좋아진다.**

이유는 단순하다 — **알고 있는 쪽(서버)이 말하기 때문.**
폴링은 모르는 쪽(브라우저)이 계속 물어보는 구조였다.

## 6. 화면 그리는 구조의 변화 (ch06~ch07 로 이어짐)

**지금 (폴링)**
```
setInterval(1초)  ──▶  loadMoreChatMessages()  ──▶  화면 갱신
      ↑
   시간이 트리거
```

**앞으로 (SSE)**
```
SSE 이벤트 수신  ──▶  loadMoreChatMessages()  ──▶  화면 갱신
      ↑
   사건이 트리거
```

**가운데와 오른쪽은 그대로.** `loadMoreChatMessages` 를 한 글자도 안 고친다.

ch03 에서 `afterChatMessageId` 커서를 만들 때 깔아둔 복선이 여기서 회수된다.

> **"내가 가진 최대 id 보다 큰 것 = 아직 못 받은 것"**

이 규칙이 있으면 **언제 물어보든 상관없다.** 1초마다 묻든, 이벤트가 왔을 때 묻든,
재연결 후에 묻든 항상 정확한 답이 나온다.

백엔드 변경도 `write()` 안에 딱 한 줄:
```kotlin
sseEmitters.send("chat__room__$chatRoomId", "chat__messageCreated", chatMessage)
```

> 🔑 **함정 예고**: SSE 이벤트에는 메시지 데이터가 이미 담겨 있다(`data: {...}`).
> 그걸 바로 화면에 넣으면 요청을 한 번 더 안 보내도 될 것 같다. **하지만 그러면 안 된다.**
> 강의가 ch07 을 "1단계(문제 발생) → 2단계(신호로만 사용)" 로 나눠 가르치는 이유.
> 무엇이 깨지는지는 ch07 에서 값으로 추적한다.

## 7. SSE 의 한계 (ch11 WebSocket 복선)

**① 단방향** — 서버 → 브라우저만. 브라우저가 보낼 땐 별도 `POST` 필요.
우리 구조에서 메시지 작성이 `fetch POST` 로 남는 이유.

**② 브라우저 커넥션 수 제한** — HTTP/1.1 은 같은 도메인에 동시 커넥션 **6개**가 상한.
SSE 가 그중 1개를 계속 점유한다.

```
탭 1  → SSE 커넥션 1개 점유
탭 2  → 2개
 ⋮
탭 6  → 6개 ← 한도 도달
탭 7  → 🚫 다른 요청들이 대기
```

ch04 처럼 탭 여러 개로 테스트할 때 실제로 겪을 수 있다.
(HTTPS + HTTP/2 면 완화 — ch10 에서 https 를 켜는 이유 중 하나)

**③ 프록시/로드밸런서 버퍼링** — 중간 장비가 응답을 모았다 보내면 실시간성이 죽는다.
Nginx 라면 `proxy_buffering off` 필요.

→ 양방향이 필요하거나 이 제약이 걸리면 **WebSocket**. 그게 ch11.

---

## 8. 언제 무엇을 쓰나

| 상황 | 선택 |
|---|---|
| 데이터가 거의 안 변함 (하루 몇 번) | **폴링**. 커넥션 유지 비용이 더 아깝다 |
| 서버 → 클라 단방향 알림 (피드, 진행률, 로그 스트림) | **SSE**. 구현이 가장 단순 |
| 양방향 · 저지연 (채팅, 게임, 협업 편집) | **WebSocket** |
| 실시간이 아예 불필요 | 그냥 REST |

> 💡 **채팅인데 SSE 를 먼저 배우는 이유**: 우리 구조에선 "쓰기"가 REST POST 로 충분해서
> 실제로 필요한 건 단방향 알림뿐 — SSE 로 충분하다. 그런데도 ch11 에서 WebSocket 으로
> 또 바꾸는 건 **같은 문제를 다른 도구로 풀어보고 차이를 체감하려는 학습 목적**이다.

## 정리

| | 폴링 | SSE |
|---|---|---|
| 누가 시작 | 브라우저가 반복 요청 | 서버가 push |
| 트리거 | **시간** | **사건** |
| 조용할 때 | 계속 요청 | 0 |
| 지연 | 평균 간격÷2 | ~즉시 |
| 방향 | 요청-응답 | 서버→클라 단방향 |
| 커넥션 | 매번 새로 (또는 keep-alive 재사용) | 1개 유지 |
| 우리 코드 영향 | — | **`loadMoreChatMessages` 무수정, 백엔드 1줄 추가** |
