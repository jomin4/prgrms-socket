## 1. 이 프로젝트가 뭔가

스프링부트(Kotlin) + React 멀티 채팅방에 **폴링 → SSE → WebSocket(STOMP)** 를 단계적으로
도입하며 실시간 통신을 익히는 **학습 프로젝트**. 결과물이 목적이 아니라 **학습이 목적**입니다.

- 원본 강의: https://www.slog.gg/p/14135 (장희성, 12강)
- 원본 백엔드: https://github.com/jhs512/p-14135-1 (태그 `0001` `0005` `0009` `0010` `0012`)
- 내 레포: https://github.com/jomin4/prgrms-socket

## 3. 한 챕터 사이클 (반드시 이 순서)

```
① 코드 조각 제시  →  ② 그 조각 설명  →  (다음 조각 반복)
        ↓
③ 사용자 승인  →  ④ Claude 가 파일에 반영
        ↓
⑤ 사용자가 직접 실행/확인  →  ⑥ Claude 가 커밋·태그·푸시 (묻지 않고 자동)
```

- **승인 전에는 파일을 건드리지 않는다.** 채팅에 코드블록으로만 보여준다.
- 승인되면 **Claude 가 파일을 직접 쓴다** (사용자 타이핑 아님 — 초반엔 타이핑이었으나 변경됨).
- **⑤ 확인이 끝난 뒤에 커밋한다.** 확인 전 커밋 금지.

## 4. 설명 방식 (사용자가 명시적으로 요구한 것)

### 4-1. 단계적으로 쪼갠다
파일 전체를 나열하고 뒤에서 몰아 설명하지 **않는다.**
`코드 조각 → 그 조각 설명 → 다음 조각` 순서로 붙여서 진행.
한 조각 = 애노테이션 묶음 / 필드 하나 / 메서드 하나 정도. `STEP 1`, `STEP 2` … 로 번호를 붙인다.

### 4-2. 문법을 그 자리에서 푼다
프론트 코드는 거기 등장하는 JS 문법을 **모른다고 가정**하고 설명한다.
백엔드 사람에게 익숙한 것(Kotlin 람다, `import`)에 빗대면 잘 통한다.

### 4-3. **실제 값을 추적한다** ← 가장 중요
문법과 의도만 말하고 끝내지 않는다. **구체적인 값이 어떻게 들어와서 어떻게 변하는지**를
`T0 / T1 / T2` 시점별로 추적하고, 마지막에 **상태 변화 표**로 정리한다.

예시 (ch04 에서 실제로 한 것):

| 시점 | 요청 커서 | 응답 `data` | reverse 후 | 새 커서 | `chatMessages` |
|---|---|---|---|---|---|
| T0 | 0 | `[3, 4]` | `[4, 3]` | 4 | `[4, 3]` |
| T1 | 4 | `[]` | — | 4 유지 | 변화 없음 |
| T2 | 4 | `[7]` | `[7]` | 7 | `[7, 4, 3]` |

### 4-4. 틀린 버전도 돌려본다
"`reverse()` 를 빼면 커서가 3이 되고 → 다음 폴링에서 4번을 또 받고 → key 중복 경고"
처럼 **무엇이 어떻게 깨지는지**를 값으로 보여준다. 이걸 사용자가 특히 좋아했다.

### 4-5. 앞으로의 복선을 깐다
"이 원칙이 7장에서 결정적입니다" 처럼 챕터 간 연결을 계속 상기시킨다.

## 7. 프로젝트 구조 규약

```
src/main/kotlin/com/back/
├── BackApplication.kt
├── domain/<도메인>/<하위도메인>/{controller,entity,service}/
└── global/<공통기능>/                ← SSE, STOMP 설정 등 도메인 무관 인프라
src/main/resources/
├── application.yaml
└── static/index.html                 ← 프론트 전체 (단일 파일)
```

- 패키지 루트 `com.back` (컴포넌트 스캔 기준점 — 이 밖에 두면 빈 등록 안 됨)
- **DB 없음.** 컨트롤러 안 인메모리 컬렉션으로 상태 유지 (싱글톤 빈이라 유지됨)
- 프론트는 **빌드 없이** React ESM(esm.sh) + Babel Standalone + Tailwind CDN
- API 호출은 **상대경로**(`/api/...`) — 같은 오리진이라 ch10 https 전환 시 프론트 수정 불필요

## 8. 지금까지 확정된 설계 결정

| 결정 | 이유 |
|---|---|
| 프론트를 CodePen 이 아니라 `static/index.html` 에 둠 | 내 코드가 git 에 남고, CORS·HTTPS 이슈 회피 |

### ch09 에서 할 일 (코드 챕터 — 파일 2개)

**파일 1/2 백엔드**: `ApiV1ChatMessageController` 에 `/entry` `/exit` 엔드포인트 추가.
**파일 2/2 프론트**: `static/index.html` 에 방 이동 버튼 + 시스템 메시지 리스너 + 입퇴장 호출.
**전체 코드는 [`02-reference.md`](02-reference.md) 의 "ch09" 절에 있음.**

이 챕터의 반전 (반드시 짚을 것):
- 시스템 메시지는 `chatMessagesByRoomId` 에 **저장하지 않고 발행만** 한다.
  → **커서로 다시 못 가져온다** → 프론트가 `e.data` 를 **직접 써야 하는 유일한 예외**.
  ch07 에서 "직접 쓰지 마라" 했던 것과 왜 다른지 대비해서 설명할 것.
  (핵심 기준: **서버에 저장돼서 다시 조회할 수 있는가?**)
- id 는 소비하므로 일반 메시지 번호에 **구멍이 생긴다** — 관찰거리로 던져줄 것.

프론트 순서 문제 (강의 9강 1단계가 고치는 것):
- **기존 메시지 로딩이 끝난 뒤에** 입장 알림을 보내야 한다.
  안 그러면 "입장했습니다" 가 옛날 메시지들보다 **위에** 떠버린다.
  → `await _loadMoreChatMessages()` 후에 `POST /entry`.
- 방 이동 시 `lastChatMessageId.current = 0` + `setChatMessages([])` 리셋 필수.
  안 하면 이전 방 메시지가 남고 커서가 이어져 새 방 메시지를 못 받는다.
- cleanup 이 이제 두 가지 일을 한다: `eventSource.close()` + `POST /exit`.
