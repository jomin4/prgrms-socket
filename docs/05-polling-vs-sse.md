# ch05 — 폴링 vs SSE: 개념과 비용

> 코드가 없는 **개념 챕터**입니다. ch04 에서 직접 만든 폴링의 비용을 **숫자로** 확인하고,

>
> 관련 질문 기록: [`qna/003`](qna/003-sseemitter-비동기-서블릿.md) ·
> [`qna/004`](qna/004-http2-멀티플렉싱.md)

## STEP 1. ch04 에서 우리가 만든 것

`static/index.html` 에 이 줄이 있습니다.

```js
const intervalId = setInterval(loadMoreChatMessages, 1000);
```

시간축으로 펼치면 이렇습니다. (아무도 말 안 하는 조용한 방)

| 시각 | 브라우저 동작 | 서버 응답 | 얻은 정보 |
|---|---|---|---|
| T+1s | `GET .../messages?afterChatMessageId=42` | `[]` | 없음 |
| T+2s | `GET .../messages?afterChatMessageId=42` | `[]` | 없음 |
| T+3s | `GET .../messages?afterChatMessageId=42` | `[]` | 없음 |
| … | … | … | … |
| T+60s | 60번째 요청 | `[]` | 없음 |

Network 탭에서 직접 본 그 `[]` 행렬입니다. **1분에 60번 물어보고 60번 "없어"를 들었습니다.**

핵심은 "쓸데없는 요청이 많다"가 아니라,
**폴링은 서버에 새 정보가 있든 없든 요청 수가 똑같다**는 점입니다.
요청 수가 *대화량*이 아니라 ***접속자 수 × 시간***에만 비례합니다.
이 성질이 아래 모든 계산을 지배합니다.

---

## STEP 2. 요청 1건의 진짜 크기

`[]` 응답의 body 는 **2바이트**입니다. 그런데 실제로 오간 건 2바이트가 아닙니다.

```
--- 요청 (브라우저 → 서버) ---
GET /api/v1/chat/rooms/2/messages?afterChatMessageId=42 HTTP/1.1
Host: localhost:8080
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...
Accept: */*
Accept-Encoding: gzip, deflate, br
Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8
Referer: http://localhost:8080/
sec-ch-ua: "Chromium";v="120", ...
Connection: keep-alive
                                              → 대략 600 ~ 800 바이트

--- 응답 (서버 → 브라우저) ---
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2
Date: Fri, 07 Aug 2026 12:00:01 GMT
Keep-Alive: timeout=60
                                              → 대략 150 ~ 200 바이트
[]                                            → 2 바이트
```

**의미 있는 데이터 2바이트를 받으려고 헤더 약 800바이트를 왕복시켰습니다.**
유효 정보 비율이 0.2% 수준입니다.

> **직접 확인법**: DevTools → Network → 요청 클릭 → **Headers 탭** 에 위 헤더가 그대로 보이고,
> 목록의 **Size 열**에 실제 전송량(대략 400~900 B)이 찍힙니다.
> `[]` 인데 Size 가 0.5 kB 쯤 나옵니다.

여기서 핵심 통찰 하나:
**HTTP 요청의 고정비(헤더)는 body 와 무관하게 매번 다시 냅니다.**
요청을 100번 하면 헤더도 100번 보냅니다. 뒤에서 SSE 가 이기는 지점이 정확히 여기입니다.

## STEP 3. 접속자가 늘면 — 숫자로

요청 1건 왕복 **0.8 KB**, 폴링 간격 **1초** 기준.

| 동시 접속자 | 초당 요청 | 하루 요청 수 | 하루 트래픽 |
|---:|---:|---:|---:|
| 1명 | 1 | 86,400 | 69 MB |
| 10명 | 10 | 864,000 | 691 MB |
| 100명 | 100 | 8,640,000 | 6.9 GB |
| 1,000명 | 1,000 | 86,400,000 | 69 GB |
| 10,000명 | 10,000 | 864,000,000 | 691 GB |

```
하루 요청 수 = 접속자 N × (1 / 폴링간격) × 86,400
```

**아무도 대화하지 않아도 이 표의 숫자는 그대로 나옵니다.**
새벽 4시에 접속자 1,000명이 채팅창을 켜둔 채 자고 있어도 초당 1,000 요청이 서버를 때립니다.
스프링 입장에서 전부 진짜 요청이라 톰캣 스레드를 잡고, 컨트롤러를 타고, JSON 직렬화까지 다 합니다.

## STEP 4. 지연(latency) — 폴링의 근본적 딜레마

방에 A, B 두 명. B의 폴링이 매초 정각(`T+0.0`, `T+1.0`, `T+2.0` …)에 돈다고 하면:

| 경우 | A가 메시지 보낸 시각 | B의 다음 폴링 | B가 보는 지연 |
|---|---|---|---|
| 운 좋음 | T+0.95 | T+1.0 | **0.05초** |
| 보통 | T+0.5 | T+1.0 | **0.5초** |
| 운 나쁨 | T+1.01 | T+2.0 | **0.99초** |

A가 보내는 시각은 폴링 시계와 무관하므로 0~1초에 균등하게 흩어집니다. 따라서

```
평균 지연 = 폴링 간격 ÷ 2
최악 지연 = 폴링 간격
```

지연을 줄이려면 간격을 줄이면 됩니다. 그런데:

| 폴링 간격 | 평균 지연 | 100명 기준 하루 요청 |
|---:|---:|---:|
| 10초 | 5초 | 864,000 |
| 5초 | 2.5초 | 1,728,000 |
| **1초** | **0.5초** | **8,640,000** |
| 0.2초 | 0.1초 | 43,200,000 |
| 0.05초 | 0.025초 | 172,800,000 |

**지연을 1/5로 줄이면 요청이 정확히 5배가 됩니다.** 반비례라 탈출구가 없습니다.
실시간에 가까워질수록 비용이 선형으로 폭발하고, 비용을 줄이면 그만큼 느려집니다.

폴링으로는 이 곡선 **위의 한 점**을 고를 수만 있지, 곡선 자체를 벗어날 수 없습니다.
**SSE 는 이 곡선을 버리는 방법입니다.**

## STEP 5. 곁가지 — "무엇을" 가져올 것인가 (전체 vs 증분)

폴링에는 축이 두 개 있습니다. **"언제 가져오나"**(STEP 1~4)와 **"무엇을 가져오나"**.
후자는 ch03/ch04 에서 이미 정했습니다.

```js
// ❌ 전체 방식 — 매번 방의 모든 메시지를 다시 받아서 통째로 교체
fetch(`/api/v1/chat/rooms/${chatRoomId}/messages`)
  .then(r => r.json())
  .then(setChatMessages);          // 있던 걸 버리고 새로 그림
```

```js
// ✅ 우리가 쓴 증분 방식
fetch(`.../messages?afterChatMessageId=${lastChatMessageId.current}`)
  .then(r => r.json())
  .then(data => {
    if (data.length > 0) {
      data.reverse();
      lastChatMessageId.current = data[0].id;
      setChatMessages(prev => [...data, ...prev]);   // 앞에 붙이기만
    }
  });
```

메시지 1,000개 쌓인 방에서 비교하면:

| | 전체 방식 | 증분 방식 |
|---|---|---|
| 폴링 1회 응답 크기 | 1,000개 × 약 150B ≈ **150 KB** | 새 게 없으면 **2 B** |
| 100명 × 1초 폴링 | **15 MB/s** | **0.02 MB/s** |
| React 렌더 | 1,000개 전부 재조정 | 새 요소만 추가 |
| 스크롤 위치 | 매번 튐 | 유지됨 |

증분 방식은 폴링을 유지한 채로 **응답 크기**를 없앴습니다.
하지만 **요청 횟수는 그대로**입니다(여전히 초당 100건).
STEP 2 에서 봤듯 요청 1건의 고정비는 헤더 800바이트인데, body 를 2바이트로 줄여도 이건 남습니다.

> **증분 조회는 "무엇을"의 낭비를 없앴고, SSE 는 "언제"의 낭비를 없앱니다.**
> 둘은 경쟁이 아니라 조합입니다 — ch07 에서 실제로 둘 다 씁니다.

## STEP 6. SSE 는 무엇을 바꾸나

### 시퀀스 비교

```
[ 폴링 ]  요청-응답을 1초마다 새로 맺는다

브라우저                                서버
   |---- GET(헤더 800B) ---------------->|   T+1s
   |<--- 200 [] (헤더 200B) -------------|
   |---- GET(헤더 800B) ---------------->|   T+2s
   |<--- 200 [] (헤더 200B) -------------|
   |---- GET(헤더 800B) ---------------->|   T+3s   ← 이 사이(T+2.4s)에 A가 메시지 보냄
   |<--- 200 [{...}] --------------------|          0.6초 늦게 도착
   |---- GET(헤더 800B) ---------------->|   T+4s
   |<--- 200 [] -------------------------|


[ SSE ]  커넥션 하나를 열어두고, 서버가 필요할 때만 밀어준다

브라우저                                서버
   |---- GET /sse/connect (헤더 800B) -->|   T+0s   ← 딱 한 번
   |<=== 200, 연결 유지 =================|
   |                                     |
   |          (조용함 — 0 바이트)         |   T+1s ~ T+2.4s
   |                                     |
   |<--- data: 43\n\n  (약 10 B) --------|   T+2.4s  ← A가 보내자마자
   |                                     |
   |          (조용함 — 0 바이트)         |
```

### 결정적 차이 세 가지

**① 헤더를 딱 한 번만 낸다.**
연결할 때 800바이트 한 번. 그 뒤 이벤트는 `data: 43\n\n` — **약 10바이트**.
HTTP 헤더가 아예 없습니다. 이미 열린 TCP 스트림에 바이트만 흘려보내는 것이라서요.

**② 조용하면 트래픽이 0이다.**
폴링은 조용해도 초당 N건. SSE 는 새벽 4시에 1,000명이 접속해 있어도 오가는 바이트가 **0**.

**③ 지연이 "간격 ÷ 2" 에서 "네트워크 왕복시간" 으로 바뀐다.**
기다릴 간격이라는 게 없습니다. 서버가 저장하는 즉시 씁니다. 로컬이면 1ms 미만.

### 같은 시나리오, 같은 숫자로 재계산

방에 **100명**, 폴링 간격 1초 기준.
SSE 쪽은 ch07 에서 쓸 **"신호로만 쓰는"** 방식(이벤트를 받으면 클라가 증분 GET 1회)으로 계산.

| 방의 활발도 | 폴링 (하루 요청) | SSE (하루 요청) | 절감 |
|---|---:|---:|---:|
| 5초당 1메시지 (매우 활발) | 8,640,000 | 1,728,000 GET + 1,728,000 이벤트 | **5배** |
| 1분당 1메시지 (보통) | 8,640,000 | 144,000 GET + 144,000 이벤트 | **60배** |
| 10분당 1메시지 (한산) | 8,640,000 | 14,400 GET + 14,400 이벤트 | **600배** |
| 아무 말 없음 | 8,640,000 | **0** | **∞** |
| 평균 지연 | 0.5초 | ~0초 | — |

여기서 읽어야 할 것은 "5배"가 아니라 **표의 모양**입니다.
폴링 열은 활발도와 무관하게 **8,640,000 고정**이고, SSE 열은 대화량에 정확히 비례합니다.

> **폴링 비용 ∝ 접속자 × 시간**
> **SSE 비용 ∝ 실제 메시지 수**

실제 채팅방은 대부분의 시간이 조용하므로 표의 아래쪽(60~600배)이 현실입니다.
그리고 지연은 활발도와 무관하게 **항상** SSE 가 이깁니다.

## STEP 7. SSE 의 한계 네 가지

**① 단방향이다 (서버 → 클라이언트).**
SSE 로는 클라가 서버에 못 보냅니다. 그래서 ch07 이후에도 **메시지 전송은 여전히 `POST /messages`**.
보내는 건 HTTP, 받는 건 SSE — 채널이 둘로 갈라집니다.
이 비대칭을 하나로 합치는 게 **WebSocket(ch11)** 입니다.

**② HTTP/1.1 에서 브라우저는 오리진당 커넥션을 6개만 연다.**
SSE 가 그중 1개를 영구 점유합니다. 탭을 6개 열면 6개가 다 SSE 로 차서
**일반 API 요청이 아예 안 나갑니다.** 무한 로딩처럼 보이는데 서버는 멀쩡해서 원인 찾기가 어렵습니다.
HTTP/2 는 멀티플렉싱으로 이 제한이 사라지는데, 브라우저는 **HTTP/2 를 TLS 위에서만** 씁니다.
→ **ch10 에서 HTTPS 를 붙이는 실용적인 이유가 이것입니다.** ("자물쇠 아이콘 붙이기"가 아님)
자세히: [`qna/004-http2-멀티플렉싱.md`](qna/004-http2-멀티플렉싱.md)

**③ 커넥션이 끊어진다.**
프록시·로드밸런서·모바일 네트워크가 유휴 커넥션을 끊습니다.
`EventSource` 는 **자동 재연결**합니다(기본 3초). 서버 쪽은 `SseEmitter` 에 타임아웃이 있고,
죽은 emitter 를 목록에서 걷어내야 합니다.
→ **ch06 의 `SseEmitters` 클래스가 정확히 이 뒤처리를 하는 코드입니다.**

**④ 커넥션을 서버가 들고 있어야 한다.**
접속자 1,000명 = 소켓 1,000개 + `SseEmitter` 객체 1,000개.
다만 Spring MVC 의 `SseEmitter` 는 **비동기 서블릿**이라 톰캣 워커 스레드는 즉시 반납됩니다
(스레드 1,000개가 아닙니다). 대신 이 목록을 여러 스레드가 동시에 건드리므로
자료구조를 잘 골라야 합니다.
→ **ch06 에서 `ConcurrentHashMap` + `CopyOnWriteArrayList` 를 쓰는 이유입니다.**
자세히: [`qna/003-sseemitter-비동기-서블릿.md`](qna/003-sseemitter-비동기-서블릿.md)

## STEP 8. 그래서 언제 뭘 쓰나

| 상황 | 선택 | 이유 |
|---|---|---|
| 상태가 몇 분에 한 번 바뀌고, 지연 몇 초 OK | **폴링** | 서버 코드 0줄. 상태 관리 없음 |
| 배치 진행률, 알림, 주가, **채팅 수신** | **SSE** | 서버→클라 단방향이면 충분. HTTP 그대로라 인프라 친화적 |
| 양방향 고빈도 — 게임, 협업 편집, 화상 시그널링 | **WebSocket** | 클라→서버도 즉시. 프로토콜 오버헤드 최소 |

폴링을 무조건 나쁜 것으로 배우면 안 됩니다.
**접속자가 적고 갱신이 드물면 폴링이 정답입니다.** ch04 에서 폴링을 먼저 만든 것도 그래서입니다.
문제는 "실시간 채팅 + 접속자 다수" 라는 우리 요구사항에서 폴링이 STEP 4 의 곡선에 갇힌다는 점입니다.

## STEP 9. ch06 / ch07 복선

ch07 에서 SSE 를 프론트에 붙일 때 이렇게 하고 싶어집니다.

```js
// ❌ 메시지 내용을 SSE 로 직접 받기
eventSource.onmessage = (e) => {
  const newMessage = JSON.parse(e.data);
  setChatMessages(prev => [newMessage, ...prev]);
};
```

"어차피 서버가 밀어주는데 메시지 자체를 실어보내면 GET 이 필요 없잖아?" — 맞는 말처럼 들리지만
**깨집니다.** 왜 깨지는지가 ch07 의 핵심(강의 미션1)입니다. 지금은 결론만:

> **SSE 는 "데이터"가 아니라 "신호"로 쓴다.**
> 서버는 "새 거 생겼어"만 쏘고, 클라는 그 신호를 받아 `afterChatMessageId` 로 증분 GET 을 한다.

ch04 의 `loadMoreChatMessages` 를 **버리지 않고 그대로 씁니다.**
바뀌는 건 그걸 부르는 주체뿐입니다.

```js
const intervalId = setInterval(loadMoreChatMessages, 1000);   // ch04
eventSource.onmessage = loadMoreChatMessages;                 // ch07 (미리보기)
```

STEP 5 의 "증분 조회와 SSE 는 경쟁이 아니라 조합" 이 이 뜻입니다.

## 정리

| | 폴링 | SSE | WebSocket |
|---|---|---|---|
| 방향 | 클라 → 서버 (요청) | 서버 → 클라 | 양방향 |
| 커넥션 | 매번 새로 | 1개 유지 | 1개 유지 |
| 요청당 헤더 | 매번 약 800 B | 최초 1회만 | 최초 1회만 |
| 조용할 때 트래픽 | 접속자 × 초당 1건 | **0** | **0** |
| 평균 지연 | 간격 ÷ 2 | ~0 | ~0 |
