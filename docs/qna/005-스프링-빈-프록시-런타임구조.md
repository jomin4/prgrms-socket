# Q005. JVM 안에서 스프링은 애노테이션·객체·프록시를 어떻게 처리하나?

**챕터**: ch11 · **날짜**: 2026-08-18

---

## 1. 애노테이션은 스스로 아무 일도 하지 않는다

`@Component` 라고 쓴다고 객체가 생기지 않는다.
애노테이션은 **클래스 파일에 붙은 메타데이터**일 뿐이다.
주석과 다른 점은 컴파일 후에도 `.class` 안에 남아 **리플렉션으로 읽을 수 있다**는 것뿐.

```
@Component
class SseEmitters { ... }
        ↓ 컴파일
SseEmitters.class  ─ "RuntimeVisibleAnnotations: @Component" 표시가 들어있음
```

**그걸 읽고 행동하는 주체는 따로 있다.** 그것이 스프링 컨테이너다.

---

## 2. 부팅 — 스캔부터 주입까지

`runApplication<BackApplication>()` 실행 시:

```
① @SpringBootApplication 안의 @ComponentScan 발동
      기준점: BackApplication 이 있는 패키지 = com.back
      → com/back/**/*.class 를 전부 열어봄

② 애노테이션이 붙은 클래스마다 "빈 정의(BeanDefinition)" 등록
      ApiV1ChatRoomController      ← @RestController
      ApiV1ChatMessageController   ← @RestController
      SseController                ← @RestController
      SseEmitters                  ← @Component
      StompSimpleBrokerConfig      ← @Configuration

      ⚠️ 아직 객체는 하나도 없다. "이런 걸 만들어야 한다"는 설계도만 모은 상태.

③ 설계도대로 객체 생성 (기본 스코프 = 싱글톤)
      new SseEmitters()                                ← 평범하게
      new StompSimpleBrokerConfig$$SpringCGLIB$$0()    ← 프록시로 감싸서

④ 생성자가 요구하는 타입을 찾아 꽂음
      SseController(sseEmitters)                        ← ③의 그 객체
      ApiV1ChatMessageController(sseEmitters, template) ← 같은 객체 + 템플릿
```

### ④가 이 프로젝트를 굴러가게 한 핵심

`SseController` 가 `connect()` 로 등록한 커넥션에
`ApiV1ChatMessageController` 가 `send()` 로 발행할 수 있는 이유는
**둘이 받은 것이 같은 객체 하나**이기 때문이다.

ch02 의 "컨트롤러 필드인데 왜 요청마다 초기화가 안 되지?" 도 같은 이유다.
③에서 객체가 딱 하나만 만들어졌으므로 요청 1000개가 전부 같은 객체를 쓴다.

> 뒤집으면: 컨트롤러 필드에 요청별 상태를 두면 **다른 사용자와 공유된다.**
> 우리는 일부러 그러고 있지만, 실무에서 `private var currentUser` 같은 걸
> 컨트롤러 필드에 두면 심각한 사고가 난다.

## 3. `@Configuration` 만 프록시로 감싸는 이유

일반적인 설정 클래스는 이렇게 생겼다.

```kotlin
@Configuration
class SomeConfig {
    @Bean fun a() = A()
    @Bean fun b() = B(a())   // ← a() 를 직접 호출!
}
```

`b()` 안의 `a()` 가 평범한 메서드 호출이면 `A` 객체가 **또** 만들어져 싱글톤이 깨진다.

**CGLIB 프록시가 이를 가로챈다.**

```
b() 안에서 a() 호출
   ↓ 프록시가 가로챔
"이미 컨테이너에 A 빈이 있나?" → 있으면 그걸 반환
   ↓
항상 같은 A 객체
```

프록시는 **원본 클래스를 상속한 자식 클래스를 런타임에 생성**해 메서드를 오버라이드한다.
따라서 **원본이 `final` 이면 안 된다.**

**Kotlin 클래스는 기본이 `final`.**
ch01 에서 넣은 `kotlin("plugin.spring")` 이 `@Configuration`·`@Component` 등이 붙은
클래스에 자동으로 `open` 을 붙여준다. 없으면:

```
Cannot subclass final class StompSimpleBrokerConfig
```

### 우리 경우의 솔직한 사실

`StompSimpleBrokerConfig` 에는 `@Bean` 메서드가 **하나도 없다** (`override fun` 두 개뿐).
그래서 **프록시가 실제로 할 일이 없다.** 그래도 `@Configuration` 이라 감싸진다.

`@Configuration(proxyBeanMethods = false)` 로 끄면 프록시 없이 조금 더 빨리 뜬다.
스프링 부트 내부 설정 클래스들은 실제로 그렇게 되어 있다.

## 4. `@EnableWebSocketMessageBroker` 가 만드는 것

`SimpleBroker`, `SimpMessagingTemplate` 은 우리가 만들지 않았다.
이 애노테이션 하나가 만든다.

```
@EnableWebSocketMessageBroker
   ↓ @Import(DelegatingWebSocketMessageBrokerConfiguration::class)
그 설정 클래스가 빈으로 등록됨
   ↓ 그 안에서
"WebSocketMessageBrokerConfigurer 타입 빈을 전부 모아와라"
   ↓ 컨테이너에서 찾음
   → StompSimpleBrokerConfig 발견 (그 인터페이스를 구현했으니)
   ↓ 우리 메서드를 호출
   registerStompEndpoints(registry)   → "/ws 를 등록해줘"
   configureMessageBroker(registry)   → "/topic 은 브로커, /app 은 내 코드"
   ↓ 그 설정대로 실제 빈 생성
   SimpleBrokerMessageHandler, SimpMessagingTemplate,
   clientInboundChannel, clientOutboundChannel, WebSocketHandlerMapping ...
```

**우리는 "설정을 말해주는 쪽"이지 "만드는 쪽"이 아니다.**
`override fun` 두 개는 프레임워크가 우리에게 묻는 질문에 답하는 것.
이 패턴을 **콜백 기반 설정**이라 한다.

| | ch06 SSE | ch11 STOMP |
|---|---|---|
| 브로커 | **내가 짬** (`SseEmitters` 39줄) | 프레임워크가 만듦 |
| 내가 하는 일 | 자료구조·동시성·정리 직접 관리 | **설정만 말해줌** |
| 통제력 | 전부 내 손안 | 프레임워크에 위임 |

ch06 에서 손으로 만들어봤기 때문에 `SimpleBroker` 가 안에서 뭘 하는지 알 수 있다.

## 5. 요청 하나가 JVM 안을 흐르는 경로

### A. 일반 REST — `POST /api/v1/chat/rooms/2/messages`
```
브라우저 → 톰캣 소켓 → DispatcherServlet
   → HandlerMapping 이 URL 로 핸들러 찾음 → ApiV1ChatMessageController.write()
   → 주입받은 sseEmitters.send(...) + messagingTemplate.convertAndSend(...)
   → 응답 쓰고 연결 닫음, 스레드 반납
```

### B. SSE — `GET /sse/connect/chat__room__2`
```
브라우저 → DispatcherServlet → SseController.connect()
   → SseEmitter 반환
   → 서블릿 비동기 전환, 스레드 반납, 소켓은 열어둠
   → 이후 A 가 실행될 때 그 소켓으로 바이트가 흘러나감
```

### C. WebSocket — `GET /ws` (핸드셰이크)
```
브라우저 → DispatcherServlet → WebSocketHandlerMapping
   → 핸드셰이크 성공 → HTTP 101 Switching Protocols
   → ★ 여기부터 DispatcherServlet 을 안 거친다
   → 이후 STOMP 프레임은 톰캣 WebSocket 계층
     → SubProtocolWebSocketHandler → SimpleBroker
```

### ★ 가 설명해주는 것

**`@CrossOrigin` 이 WebSocket 에 안 먹히는 이유가 이것이다.**
`@CrossOrigin` 은 `RequestMappingHandlerMapping`(컨트롤러 매핑)이 읽는 설정인데,
핸드셰이크는 `WebSocketHandlerMapping` 이 처리한다.
그래서 `setAllowedOrigins(...)` 를 따로 지정해야 한다.

---

## 한 문장 요약

**애노테이션은 표시일 뿐**이고, 스프링 컨테이너가 부팅 때 그것을 읽어
**타입당 객체 하나씩(싱글톤)** 만들어 서로 꽂아둔다.
그 객체 그래프가 **JVM 이 살아있는 동안 그대로 유지**되고,
브라우저의 모든 요청은 그 위를 지나갈 뿐이다.
