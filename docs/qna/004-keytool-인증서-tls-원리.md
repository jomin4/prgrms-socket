# Q004. `keytool` 은 무엇을 만들고, 서버와 브라우저는 어떻게 증명하나?

**챕터**: ch10 · **날짜**: 2026-08-18

```bash
keytool -genkey -alias sb-ssl -storetype PKCS12 -keyalg RSA -keysize 2048 -keystore keystore.p12 -validity 3650
```

---

## 1. 비대칭 암호 — 열쇠가 두 개인 이유

일반 자물쇠는 잠근 열쇠로 연다(대칭). RSA 는 다르다.

```
공개키로 잠금  →  개인키로만 열림     ← "암호화"에 씀
개인키로 잠금  →  공개키로만 열림     ← "서명"에 씀  ★ 핵심
```

두 번째가 전부다. **개인키를 가진 사람만 만들 수 있는데, 공개키로 누구나 확인할 수 있는 값**
— 그것이 서명이다. 도장은 나만 갖고 있고, 도장 자국은 누구나 대조할 수 있는 것과 같다.

`-keysize 2048` 은 이 수학 문제의 크기. 공개키로부터 개인키를 역산하는 것이
현재 기술로 불가능한 수준이 2048비트다.

---

## 2. `keytool` 이 실제로 만드는 것

```
① RSA 2048 키 쌍 생성
      개인키 (서버만 보관)  ←수학적 짝→  공개키 (공개)

② 인증서 조립
      [ 공개키 ] + [ 신원 CN=Unknown · 유효기간 10년 ] + [ 서명 ]
                                                          ↑ 위의 개인키로 만듦
③ keystore.p12 에 담고 비밀번호로 암호화
      { 개인키, 인증서 }  ← 123456
```

### 왜 공개키만 달랑 보내면 안 되나

중간에서 누가 가로채 **자기 공개키로 바꿔치기**하면 브라우저는 알 방법이 없다.
그대로 통신하면 전부 읽힌다(중간자 공격).

그래서 공개키를 신원정보와 함께 묶고 **서명**을 붙인다.

**서명이 보장하는 것 두 가지**
1. **위조 불가** — 서명을 만들려면 그 개인키가 있어야 한다
2. **변조 감지** — 내용을 한 글자만 바꿔도 해시가 달라져 검증이 깨진다

---

## 3. 자가서명 vs 진짜 인증서 — 딱 한 곳이 다르다

**서명을 누구의 개인키로 만들었느냐** 뿐이다.

```
진짜 인증서 (Let's Encrypt 등)
  내 공개키  ←서명—  CA 의 개인키
                       ↑ CA 의 공개키는 브라우저/OS 에 미리 내장 → 검증 가능 ✅

자가서명 (우리)
  내 공개키  ←서명—  내 개인키
                       ↑ 내 공개키는 아무도 미리 안 갖고 있음 → 검증 근거 없음 ⚠️
```

브라우저·OS 에는 신뢰할 수 있는 **루트 CA 인증서 수백 개**가 이미 깔려 있다.
자가서명은 "제가 저인 걸 제가 증명합니다" 라서 논리적으로 의미가 없다.

> 그래서 `keytool` 프롬프트의 이름·조직·국가를 **전부 빈칸**으로 둬도 된다.
> 어차피 아무도 검증하지 않는다. `CN=Unknown` 이 그대로 인증서에 박힌다.

## 4. TLS 핸드셰이크 — 서버가 자기를 증명하는 순간

```
브라우저                                              서버
   │                                                   │
   │──── ① 인사 + 내 임시 공개값 ────────────────────▶│
   │                                                   │
   │◀─── ② 인증서 + 개인키로 만든 서명 ────────────────│
   │                                                   │
   │  ③ 검증                                           │
   │     A. 인증서의 공개키로 ②의 서명 확인            │
   │     B. 발급자가 신뢰된 CA 인지 확인               │
   │                                                   │
   │◀─── ④ 같은 세션키 도출 → AES 대칭키 암호화 ─────▶│
```

②의 서명은 인증서 안에 든 서명이 아니라 **지금 이 대화 내용에 대해 방금 만든 새 서명**이다.

### ③이 증명하는 것 — 두 검사는 별개다

| 검사 | 방법 | 우리 경우 |
|---|---|---|
| **A. 이 서버가 인증서의 진짜 주인인가?** | 인증서 안의 **공개키**로 ②의 서명 검증 | ✅ **통과** |
| **B. 이 인증서를 믿을 수 있나?** | 발급자를 따라 올라가 신뢰된 루트 CA 에 닿는지 | ❌ **실패** |

**A 가 핵심이다.** 인증서는 공개 문서라 누구나 복사할 수 있다.
네이버 인증서를 다운받아 내 서버에 붙일 수도 있다.

하지만 **개인키는 훔칠 수 없다.** 그래서 브라우저가 "이 대화에 서명해봐" 라고 요구한다.
인증서에 든 공개키로 그 서명이 풀린다면 → **개인키를 갖고 있다는 증거**다.

```
인증서를 훔친 가짜 서버
   → 인증서는 보낼 수 있음
   → 개인키가 없어 서명을 못 만듦
   → ③-A 에서 걸림 ✅
```

우리 서버는 개인키를 진짜로 갖고 있으므로 **A 는 통과**한다. **B 만 실패**한다.

### ④ 왜 대칭키로 갈아타나

비대칭 암호는 대칭 암호보다 **수백~수천 배 느리다.**
그래서 "느리지만 안전한 방법으로 열쇠만 합의하고, 실제 데이터는 빠른 방법으로" 라는 구조다.

①②에서 주고받은 임시 공개값으로 양쪽이 **같은 세션키를 각자 계산**해낸다.
그 값 자체는 네트워크에 흐르지 않는다(디피–헬만).
이후 모든 통신은 그 세션키로 **AES 대칭키 암호화**된다.

## 5. 경고 화면이 정확히 뜻하는 것

```
NET::ERR_CERT_AUTHORITY_INVALID
연결이 비공개로 설정되어 있지 않습니다
```

**"암호화가 안 된다"는 뜻이 아니다.** 번역하면:

> "이 서버와의 통신은 **정상적으로 암호화된다.**
> 다만 **상대가 진짜 localhost 인지 제3자가 보증해주지 않아서**,
> 지금 말 걸고 있는 상대가 누군지 장담할 수 없다."

**A 는 통과, B 만 실패**한 상태다.
`고급 → 계속 진행` 은 "신원 확인은 내가 알아서 할 테니 넘어가" 라는 뜻.

- **로컬 개발**: 상대가 내 PC 의 내 서버인 걸 아니까 완전히 안전
- **실서비스에서 이 경고**: 절대 그냥 넘기면 안 된다. 중간자 공격일 수 있다

경고를 통과한 뒤에도 **암호화는 100% 정상**이다.
그래서 ch11 의 `wss://` WebSocket 도 문제없이 붙는다.

## 요약

| 무엇 | 어디 있나 | 하는 일 |
|---|---|---|
| **개인키** | `keystore.p12` 안, 서버만 | **서명 생성** — 신원 증명 |
| **공개키** | 인증서 안, 누구에게나 | **서명 검증** |
| **인증서** | 서버가 브라우저에 전송 | 공개키 + 신원 + 발급자 서명 |
| **CA 서명** | (우리는 자기 자신) | 발급자 신뢰 사슬 |
| **세션키** | 핸드셰이크로 양쪽이 각자 계산 | 실제 데이터 AES 암호화 |

**한 문장**
`keytool` 은 자물쇠(공개키)와 열쇠(개인키)를 만들고,
자물쇠에 자기 이름표를 붙여 자기 도장을 찍은 뒤(자가서명 인증서),
열쇠와 함께 금고(`keystore.p12`)에 넣어 비밀번호로 잠근다.
