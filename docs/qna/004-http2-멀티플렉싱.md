# Q004. HTTP/2 멀티플렉싱이 뭔가? (그리고 왜 SSE 에 HTTPS 가 필요한가)

**챕터**: ch05 · **날짜**: 2026-08-07

ch05 STEP 7 의 "② HTTP/1.1 에서 브라우저는 도메인당 커넥션을 6개만 엽니다" 에서 나온 질문.

---

## 1. HTTP/1.1 의 구조적 문제 — HOL 블로킹

HTTP/1.1 커넥션 하나에서는 **요청 하나를 보내고 그 응답을 다 받아야 다음 요청**을 보낼 수 있습니다.

```
[ HTTP/1.1 커넥션 1개 ]

시간 →
요청A ──응답A── 요청B ──응답B── 요청C ──응답C──
        (A 끝날 때까지 B는 대기)
```

**HOL(Head-Of-Line) 블로킹** — 앞사람이 안 비키면 뒷사람이 못 갑니다.

파이프라이닝(응답을 안 기다리고 요청을 연달아 보내기)이 스펙에 있지만,
응답이 여전히 **보낸 순서대로** 와야 해서 HOL 이 안 풀립니다.
중간 프록시 호환성 문제까지 겹쳐 **모든 브라우저가 기본 비활성화**했습니다. 사실상 없는 기능.

---

## 2. 브라우저의 우회로: 커넥션 6개

병렬성을 얻으려고 브라우저는 **오리진 하나당 TCP 커넥션을 6개까지** 엽니다.

- 오리진 = `scheme + host + port` → `http://localhost:8080` 전체가 하나
- **이 한도는 탭별이 아니라 브라우저 프로필 전체에서 공유**

평소엔 문제없습니다. 요청이 짧게 끝나고 커넥션이 재사용되니까요.
문제는 **안 끝나는 응답**입니다.

---

## 3. SSE 를 켠 순간 — 값 추적

SSE 응답은 정의상 영원히 안 끝납니다. 커넥션 1개를 통째로 영구 점유합니다.

같은 브라우저에서 `http://localhost:8080` 탭을 늘려가며 각 탭이 SSE 1개씩 연다면:

| 열린 탭 수 | SSE 가 점유한 커넥션 | 남은 커넥션 | 결과 |
|---:|---:|---:|---|
| 1 | 1 | 5 | 정상 |
| 3 | 3 | 3 | 정상 |
| 5 | 5 | **1** | 모든 API 요청이 1줄로 직렬화 → 눈에 띄게 느려짐 |
| **6** | **6** | **0** | **모든 요청이 무한 Pending. 리로드조차 안 됨** |

**6번째 탭에서 서비스 전체가 멈춥니다.**
그런데 서버는 멀쩡합니다 — `curl` 은 즉시 응답하고, 서버 로그에도 아무것도 안 남습니다.
**원인이 브라우저 안에 있어서 서버만 보면 절대 못 찾습니다.**
MDN `EventSource` 문서에도 경고로 박혀 있는 유명한 함정입니다.

> ch07 이후 탭을 6개까지 늘려 직접 재현해 볼 것.

---

## 4. HTTP/2 가 바꾸는 것 — 스트림과 프레임

HTTP/2 는 커넥션 1개 안에 **스트림(stream)** 이라는 논리적 통로를 여러 개 만듭니다.
핵심은 **모든 데이터를 프레임(frame)으로 쪼개고, 각 프레임에 스트림 ID 를 붙이는 것**입니다.

```
[ HTTP/2 커넥션 1개 ]

시간 →
│HEADERS(1)│HEADERS(3)│DATA(3)│DATA(1)│DATA(3)│HEADERS(5)│DATA(5)│DATA(1)│
     ↑          ↑         ↑       ↑
   스트림1    스트림3   스트림3  스트림1     ← 뒤섞여서(인터리빙) 흐름
```

수신 측이 스트림 ID 로 재조립합니다. **순서 보장이 스트림 단위**라서
스트림 1이 안 끝나도 스트림 3, 5는 자유롭게 오갑니다. HTTP 레벨 HOL 이 사라집니다.

동시 스트림 개수는 `SETTINGS_MAX_CONCURRENT_STREAMS` 로 협상하며 보통 **100~250** 입니다.

같은 표를 HTTP/2 로 다시 그리면:

| 열린 탭 수 | TCP 커넥션 | SSE 가 쓰는 스트림 | 남은 스트림 (100 기준) | 결과 |
|---:|---:|---:|---:|---|
| 1 | 1 | 1 | 99 | 정상 |
| 6 | 1 | 6 | 94 | **정상** |
| 20 | 1 | 20 | 80 | 정상 |

문제 자체가 없어집니다.

## 5. 덤 — HPACK 헤더 압축

HTTP/2 는 헤더도 압축합니다(**HPACK**). 커넥션 단위로 **헤더 테이블**을 양쪽이 공유합니다.

```
1번째 요청:  User-Agent: Mozilla/5.0 (Windows NT 10.0...)   ← 전체 전송, 테이블 등록 (인덱스 62)
2번째 요청:  [인덱스 62]                                      ← 1~2바이트!
3번째 요청:  [인덱스 62]                                      ← 1~2바이트!
```

ch05 STEP 2 의 "폴링 요청마다 헤더 800바이트" 문제가 상당히 완화됩니다.

| | HTTP/1.1 | HTTP/2 (HPACK) |
|---|---:|---:|
| 폴링 요청 1건 헤더 | 약 800 B | 약 **30~60 B** |
| 100명 × 1초 × 하루 | 6.9 GB | 약 **0.5 GB** |

**다만 요청 횟수(하루 864만 건)는 그대로입니다.**
톰캣 스레드·컨트롤러·JSON 직렬화는 여전히 864만 번 돕니다.
HTTP/2 는 폴링의 **대역폭**만 줄여줄 뿐, 폴링을 SSE 로 만들어주지 않습니다.
ch05 STEP 4 의 "지연 ↔ 요청 수 반비례 곡선" 도 그대로 남습니다.

## 6. 왜 HTTPS 가 필요한가 — ch10 의 진짜 이유

HTTP/2 스펙은 평문(h2c)도 정의하지만, **브라우저는 h2c 를 구현하지 않았습니다.**
Chrome / Firefox / Safari 전부 **TLS 위에서만** HTTP/2 를 씁니다.

이유는 실용적입니다. 낡은 중간 프록시·방화벽이 평문 HTTP 를 들여다보고 건드려서
업그레이드가 깨지는데, TLS 로 감싸면 중간 장비가 내용을 못 보니 그대로 통과합니다.

프로토콜 선택은 TLS 핸드셰이크 중 **ALPN(Application-Layer Protocol Negotiation)** 으로 이뤄집니다.

```
브라우저 → 서버 :  ClientHello  { ALPN: ["h2", "http/1.1"] }     "난 h2 도 되는데?"
서버 → 브라우저 :  ServerHello  { ALPN: "h2" }                    "그럼 h2 로 하자"
                   ↓
             HTTP/2 로 통신 시작 (추가 왕복 없음)
```

**정리하면 이 체인입니다.**

```
멀티 탭에서 SSE 를 쓰고 싶다
   → HTTP/1.1 커넥션 6개 한도에 걸린다
   → HTTP/2 멀티플렉싱이 필요하다
   → 브라우저는 TLS 위에서만 HTTP/2 를 쓴다 (ALPN)
   → 그래서 HTTPS 가 필요하다        ← ch10
```

ch10 의 `keytool` + `server.ssl.*` 는 "보안 실습"이 아니라 **이 문제를 푸는 작업**입니다.

---

## 7. 남은 한계 — TCP 레벨 HOL 은 안 풀린다

HTTP/2 는 **HTTP 레벨** HOL 만 풀었습니다. 그 밑의 **TCP 레벨** HOL 은 남습니다.

TCP 는 바이트의 순서 도착을 보장하므로, 패킷 하나가 유실되면
**그 뒤에 도착한 모든 패킷이 재전송을 기다립니다** — 다른 스트림 것이어도.
커넥션을 1개로 합쳤기 때문에, 패킷 손실이 잦은 환경(모바일)에서는
오히려 HTTP/1.1 의 커넥션 6개가 나을 때도 있습니다.

이를 풀려고 TCP 대신 UDP 기반 QUIC 을 쓰는 것이 **HTTP/3** 입니다 (스트림별 독립 재전송).

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 계층 | TCP | TCP | QUIC (UDP) |
| 병렬 처리 | 커넥션 6개 | 스트림 100+ (커넥션 1개) | 스트림 (커넥션 1개) |
| HTTP HOL | ❌ 있음 | ✅ 해결 | ✅ 해결 |
| TCP HOL | 있음 (커넥션당) | ❌ **있음** | ✅ 해결 |
| 헤더 압축 | 없음 | HPACK | QPACK |
| SSE 커넥션 한도 | **6개** | 100+ | 100+ |

## 8. 직접 확인하는 법

DevTools → Network → 컬럼 헤더 **우클릭 → Protocol 체크**. 열이 하나 생깁니다.

| 지금 (ch04, http) | ch10 이후 (https) |
|---|---|
| `http/1.1` | `h2` |

ch10 이 끝나면 이 열이 `http/1.1` → `h2` 로 바뀌는 것을 직접 볼 수 있습니다.
그때 3절의 탭 6개 실험도 다시 해보면 — 안 멈춥니다.

## 한 줄 요약

**멀티플렉싱 = 커넥션 1개 안에서 여러 요청/응답을 프레임 단위로 뒤섞어 동시에 나르는 것.**
HTTP/1.1 은 이게 안 돼서 커넥션 6개로 우회했고, SSE 가 그 6개를 잡아먹는다.
HTTP/2 가 이를 풀지만 브라우저는 TLS 위에서만 HTTP/2 를 써서 → ch10 HTTPS 가 필요해진다.
