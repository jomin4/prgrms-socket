## 1. 세 방식 비교

| 축 | 폴링 | SSE | WebSocket(STOMP) |
|---|---|---|---|
| 트리거 | **시간** | **사건** | **사건** |
| 방향 | 요청-응답 | 단방향 (서버→클라) | **양방향** |
| 조용할 때 트래픽 | 계속 요청 | **0** | **0** |
| 평균 지연 | 간격의 절반 | 즉시 | 즉시 |
| 방 이동 비용 | 없음 (커서만 리셋) | 재연결 + 핸드셰이크 | **프레임 2개** |
| 서버 스레드 | 요청마다 점유 후 반납 | 점유 안 함 (서블릿 비동기) | 점유 안 함 |
| 필요한 것 | 없음 | 브라우저 내장 `EventSource` | SockJS + Stomp.js |
| 재연결 | 직접 구현 | **자동** | 라이브러리가 처리 |

### 언제 무엇을 쓰나

| 상황 | 선택 | 이유 |
|---|---|---|
| 데이터가 거의 안 변함 (하루 몇 번) | **폴링** | 커넥션 유지 비용이 더 아깝다 |
| 서버 → 클라 단방향 알림 (피드, 진행률, 로그) | **SSE** | 구현 가장 단순, 자동 재연결 공짜 |
| 양방향 · 저지연 (게임, 협업 편집) | **WebSocket** | 클라 → 서버도 빈번할 때 |
| 실시간이 불필요 | REST | — |

> **우리 채팅은 사실 SSE 로 충분했다.** "쓰기"가 REST POST 로 해결되니 필요한 건 단방향
> 알림뿐이었다. ch11 에서 `/app` 목적지를 한 번도 안 쓴 것이 그 증거 — **WebSocket 의
> 절반만 쓴 셈**이다.
>
> 그런데도 바꿔본 이유는 **같은 문제를 세 도구로 풀어봐야 각 도구의 값어치를 알 수 있기**
> 때문이다. ch06 에서 `SseEmitters` 를 손으로 만들어봤기 때문에 ch11 의 `SimpleBroker` 가
> 뭘 해주는지 정확히 알 수 있다.

## 2. 12챕터 동안 실제로 바뀐 것

```
ch04   setInterval(fn, 1000)   ─┐
ch07   addEventListener        ─┼─▶  loadMoreChatMessages  ─▶  GET ?afterChatMessageId  ─▶  화면
ch11   stompClient.subscribe   ─┘
       └── 여기만 바뀜 ──┘         └────────── 한 글자도 안 바뀜 ──────────┘
```

이것을 가능하게 한 것은 ch03 에서 만든 쿼리 파라미터 하나다.

> **`afterChatMessageId`** — 내 최대 id 보다 큰 것 = 아직 못 받은 것

id 를 **전역 단조증가**로 만들었기 때문에 이 규칙이 항상 성립한다.
그래서 **언제 물어보든 상관없다.** 1초마다 묻든, 이벤트가 왔을 때 묻든,
재연결 후에 묻든 항상 정확한 답이 나온다.

## 3. 이 프로젝트가 가르친 원칙 4개

### 3-1. 진실의 원천은 하나여야 한다

```
서버 = 진실의 원천
실시간 채널 = "지금 물어봐" 라는 초인종일 뿐
```

ch07 에서 SSE 의 `e.data` 를 직접 쓰면 왜 깨지는지 값으로 확인했다.
채널이 둘이 되는 순간 순서·중복·누락이 전부 살아난다.

### 3-2. 갱신은 멱등해야 한다

`loadMoreChatMessages` 는 **몇 번 호출하든, 어떤 순서로 호출하든 최종 상태가 같다.** 그래서

- ch08 쓰로틀링으로 호출을 100번 → 4번으로 줄여도 **결과가 동일**
- 네트워크가 끊겼다 붙어도 **놓친 것이 자동으로 메꿔짐**
- 응답이 뒤늦게 도착해도 **안 깨짐**

### 3-3. 트리거와 데이터 획득을 분리한다

2절의 그림이 그것. 이 분리가 없었다면 통신 방식을 바꿀 때마다
화면 그리는 로직을 다시 짜야 했다.

### 3-4. 예외는 기준을 명확히 하고 인정한다

ch09 의 시스템 메시지는 **원칙을 어긴다.** 하지만 기준이 분명했다.

> **서버에 저장돼서 다시 조회할 수 있는가?**

저장 안 되는 것은 이벤트가 유일한 원본이니 직접 쓸 수밖에 없다.
**원칙을 아는 것보다 예외의 경계를 아는 것이 더 어렵고 중요하다.**

| ch09 | `await` 없이 입장 알림 | "입장했습니다" 가 옛 메시지 아래로 밀림 |
| ch09 | 방 이동 시 리셋 누락 | 이전 방 메시지가 남고 새 방 건 못 받음 |

## 5. 이 프로젝트가 안 다룬 것 (실무로 가려면)

| 빠진 것 | 왜 필요한가 |
|---|---|
| **인증·인가** | 지금은 누구나 `/sse/connect/아무키` 로 남의 채널을 엿볼 수 있다 |
| **DB 영속화** | 서버 재시작하면 전부 사라진다 |
| **다중 서버** | `SimpleBroker` 는 서버 간 공유 안 됨 → RabbitMQ 릴레이 또는 Redis Pub/Sub |
| **정확한 퇴장 감지** | 탭을 그냥 닫으면 cleanup 이 안 돎 → 서버가 커넥션 종료를 감지해야 함 |
| **과거 메시지 페이징** | 위로 스크롤해서 옛 대화 불러오기 (`beforeChatMessageId`) |
| **재연결 백오프** | 서버가 죽었을 때 무한 재시도로 부하 주지 않기 |
| **테스트** | 지금은 테스트 코드가 하나도 없다 |

### 가장 해볼 만한 다음 과제

`SseEmitters.connect()` 의 `onCompletion` 콜백에서 **자동으로 퇴장 메시지를 발행**하게
만들어보기. 이미 콜백은 붙어 있으니 그 안에서 방 키를 파싱해 `send(...)` 를 부르면 된다.
탭을 그냥 닫아도 퇴장이 잡힌다.

STOMP 쪽은 `SessionDisconnectEvent` 를 `@EventListener` 로 받으면 같은 일을 할 수 있다.
